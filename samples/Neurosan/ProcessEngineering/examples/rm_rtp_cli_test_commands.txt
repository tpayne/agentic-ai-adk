# ============================================================
# RM / RtP robustness test script
#
# Run from samples/Neurosan/ProcessEngineering:
#   uv run python cli.py -f examples/rm_rtp_cli_test_commands.txt
#
# Exercises Requirements Management (RM) and Response to Proposal (RtP)
# end to end: missing/empty-directory edge cases, document generation,
# consultant queries, quality review, and reviewer apply-mode (identify
# issues -> fix them -> regenerate), both as a combined "review and fix"
# request and as a separate later-turn "update the document" request.
#
# Test fixtures used (already in this repo):
#   - RequirementsManagement/MetroLink_RFP_Package -- the real RFP + addendum
#   - RequirementsManagement/Healthcare_Referral_Baseline -- a second,
#     independent RM example, used for the one-shot file-based creation test
#   - ResponseToProposal/04_Bidder_Offering_Brief_Harborlight_Digital.pdf --
#     the bidder's own offering brief. proposal_response_agent has no tool
#     to read a PDF itself, so its content is paraphrased inline below as
#     the "our offering" description, exactly as a real user would type it
#     after reading the brief -- the brief's own last page ("How to use in
#     a proposal-response test") confirms this is the intended usage, and
#     explicitly calls for TBD pricing and no invented certifications/
#     references, which doubles as a built-in fabrication-avoidance test.
#
# Session state in this CLI is a mix of in-memory conversation (reset by
# "clear") and on-disk saved JSON (output/requirements_summary.json,
# output/proposal_response.json, independent of "clear"). The $ resets
# below delete the on-disk state at specific points so the NOT_FOUND/
# empty-directory negative cases, and the RtP auto-analyze positive case,
# are exercised against a genuinely clean slate rather than leftover
# state from an earlier run of this same script.
# ============================================================

$ rm -f output/requirements_summary.json output/proposal_response.json
$ rm -f output/*.docx
$ mkdir -p /tmp/rm_test_empty_dir
$ rm -rf /tmp/rm_test_missing_dir
sleep 1

# ------------------------------------------------------------

# A2. NEGATIVE: directory that exists but has no files in it

Draft our response to this proposal. We offer a configurable supplier onboarding portal.

# A4. NEGATIVE: regenerate a requirements document before anything has ever been created
Regenerate the requirements document.

# A5. NEGATIVE: regenerate a proposal response document before anything has ever been created
Regenerate the proposal response document.

# A6. NEGATIVE: bare, underspecified creation request -- should ask a clarifying question, not fabricate
Create a requirements document.

# A7. NEGATIVE: genuinely ambiguous intent -- should ask what the user wants, not guess
Can you take a look at this and tell me what you think?

# B9. Quality review AND fix in the SAME request (functional + non-functional issues)
Review the requirements for quality and fix any issues you find, including any functional \
or non-functional requirements that are vague, untestable, or missing acceptance criteria.

# B10. SEPARATE follow-up turn: a specific fix request, not combined with "review" this time
