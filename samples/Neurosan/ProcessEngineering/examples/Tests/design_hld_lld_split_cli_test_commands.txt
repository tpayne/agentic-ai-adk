# ============================================================
# HLD/LLD split design-document robustness test script
#
# Run from samples/Neurosan/ProcessEngineering:
#   uv run python cli.py -f examples/Tests/design_hld_lld_split_cli_test_commands.txt
#
# Exercises the design_variant feature end to end: creating/regenerating a design
# document used to always produce ONE combined .docx with an internal "Part I /
# Part II" split; it now always produces TWO SEPARATE, self-contained documents
# (HLD and LLD), and the caller can ask for just the HLD, just the LLD, or both,
# for BOTH creation (Design_Doc_Pipeline) and regeneration (Regenerate_Document_Agent),
# plus the update pipeline (Design_Doc_Update_Pipeline), which always renders both
# and has no variant selection of its own. Covers: nothing-saved negative cases,
# a real multi-agent generate/review creation run (default "both"), consultant
# queries against the resulting single JSON baseline (unaffected by the split --
# it still reads one design_data.json), all four regeneration phrasings (bare/
# implicit "both", explicit HLD-only, explicit LLD-only, and explicit "HLD and
# LLD" wording), a design change request proving the update pipeline's own render
# step also produces the two separate files, and -- via a genuine HLD-only
# document IMPORT (not a fabricated baseline) -- the hard ERROR case where an
# explicit LLD-only regenerate request is made against a design with no
# low_level_design content at all.
#
# Design generation itself (Design_Doc_HLD_Agent -> Design_Doc_LLD_Agent) always
# builds BOTH the high-level and low-level design content regardless of what's
# asked at render time -- this script's design_variant wording only ever
# controls which Word document(s) get RENDERED from that one JSON baseline, per
# design.hocon's own STEP 8b. The one genuine way to get a design with NO
# low_level_design content at all for the ERROR case (Part F) is a document
# IMPORT explicitly scoped to "High-Level Design only", not the normal two-stage
# creation pipeline, which always produces Combined content.
#
# Test fixture used: a small inline source document, written by this script
# itself (via "$ printf ... > file", same convention used elsewhere in this
# project's own test scripts) into a throwaway /tmp directory, describing a
# fictional Returns Processing Service's high-level architecture ONLY, with an
# explicit note that no low-level design content is provided or wanted.
#
# Session state in this CLI is a mix of in-memory conversation (reset by
# "clear") and on-disk saved JSON (output/design_data.json, independent of
# "clear"). The $ resets below delete output/design_data.json and any
# previously-rendered .docx files at specific points so each part's positive/
# negative assertions are exercised against a genuinely clean slate rather than
# leftover state from an earlier part of this same script.
# ============================================================

$ rm -f output/design_data.json output/requirements_summary.json output/cloudarch_drawio.xml
$ rm -f output/*.docx output/*.png output/*.json
sleep 1

# ------------------------------------------------------------
# PART A -- negative / edge cases (nothing saved yet)
# ------------------------------------------------------------

# A1. NEGATIVE: regenerate the design document before anything has ever been created
Regenerate the design document.

# A2. NEGATIVE: regenerate just the LLD before anything has ever been created -- distinct from Part
# F's later "something IS saved, but it has no LLD content" case; this one has NOTHING saved at all.
Please regenerate just the LLD.

# A3. NEGATIVE: bare, underspecified creation request -- no actual system/content to design from,
# should fail requirements extraction rather than inventing a generic design.
Create a design document.

# A4. NEGATIVE: genuinely ambiguous intent -- should ask what the user wants, not guess
Can you take a look at this and tell me what you think?

# ------------------------------------------------------------
# PART B -- positive creation flow, default ("both") variant
# ------------------------------------------------------------

# B1. POSITIVE: a real, substantive request with enough content to populate BOTH the High-Level
# Design and the Low-Level Design, plus quality attributes/compliance/risk so neither document is
# thin. No HLD/LLD-only wording here, so the pipeline's own default ("both") applies -- confirms TWO
# separate Word documents get rendered from this ONE request, not one combined file.
Create a Combined HLD/LLD design document for a Checkout Service: an authenticated checkout API \
that accepts cart contents, validates inventory via the Inventory Service, calculates tax and \
shipping, takes payment via the Payment Gateway, and emits an order-confirmation event once \
payment settles. It must be PCI-DSS compliant for any cardholder data, handle at least 200 \
orders/second at peak with 99.9% availability, and degrade gracefully (queue-and-retry, not fail \
outright) if the Payment Gateway is briefly unavailable. Favor a synchronous REST API Gateway in \
front of a checkout orchestration service, with asynchronous messaging to Inventory and to the \
order-confirmation event stream.

# Confirm manually: the listing below should show TWO files, safe-filenamed as
# "Checkout_Service_HLD.docx" and "Checkout_Service_LLD.docx" (exact safe_filename_component
# output may vary slightly) -- never a single "Checkout_Service.docx"/"...Combined...docx" file.
list

# ------------------------------------------------------------
# PART C -- design consultant queries (unaffected by the split -- still reads ONE JSON baseline,
# regardless of how many Word documents were rendered from it)
# ------------------------------------------------------------

What does the Checkout Service depend on?
Why is the Checkout API synchronous but order confirmation asynchronous?
Is the 99.9% availability requirement met, and by which component?

# ------------------------------------------------------------
# PART D -- regeneration: implicit "both", explicit HLD-only, explicit LLD-only, and explicit
# "HLD and LLD" wording (a different way of saying "both") -- each in its own clean slate so the
# "list" output after each unambiguously shows only what THAT request actually produced.
# ------------------------------------------------------------

# D1. POSITIVE: bare regenerate, no variant wording at all -- same implicit default as creation.
# Confirms it renders BOTH files again from the Part B baseline, not just one.
$ rm -f output/*.docx
Regenerate the design document.

list

# D2. POSITIVE: explicit HLD-only regeneration -- confirms only the HLD file is produced, and the
# agent's own reply names ONLY the HLD, not "both" and not the LLD.
$ rm -f output/*.docx
Please regenerate just the HLD.

list

# D3. POSITIVE: explicit LLD-only regeneration, in a SEPARATE later turn -- the reverse direction
# of D2, against the same still-intact Combined baseline (which has real low_level_design content
# from Part B, so this must succeed, not error).
$ rm -f output/*.docx
Regenerate just the Low-Level Design.

list

# D4. POSITIVE: "HLD and LLD" wording, phrased differently than D1's own bare/implicit default --
# confirms this phrasing also resolves to design_variant="both", not an error or a guess.
$ rm -f output/*.docx
Please regenerate the HLD and the LLD.

list

# ------------------------------------------------------------
# PART E -- design change request (Design_Doc_Update_Pipeline): confirms the split survives an
# UPDATE, not just a fresh creation or a bare regenerate. This pipeline's own generate_design_document
# tool has no design_variant parameter of its own (by design -- see registries/design_update.hocon),
# so it always renders BOTH documents regardless of wording; that is expected here, not a bug.
# ------------------------------------------------------------

# E1. POSITIVE: a real change request against the Part B baseline -- design_update.hocon's own
# canonical sample_query ("Add a rate-limiting component in front of the Checkout Service's API
# Gateway...") has NO "design"/"architecture"/"process"/"workflow" word in it at all, so per
# process_architect.hocon's own documented "2a/2b: WHY THE GATE ABOVE HAS NO STATE-BASED EXCEPTION"
# section, it ALWAYS correctly triggers Rule 10's clarifying question instead of routing straight to
# Design_Doc_Update_Pipeline -- confirmed deliberate, not a bug (three earlier rounds of real
# production bugs were caused by exactly this sentence being routed on a state-based guess instead).
# An explicit "design document" phrase added here is the actual disambiguating signal, so this
# reaches Design_Doc_Update_Pipeline directly. Confirms its own render step ALSO produces the two
# separate files, not a stale single combined one.
$ rm -f output/*.docx
Add a rate-limiting component to the design document, in front of the Checkout Service's API \
Gateway, to protect the Payment Gateway from traffic spikes, and regenerate the documents.

list

# ------------------------------------------------------------
# PART F -- the "LLD explicitly requested but the saved design has no low_level_design content at
# all" hard ERROR case. The live two-stage creation pipeline (Part B) always builds BOTH HLD and
# LLD content, so it cannot produce this state -- a genuine HLD-only document IMPORT is the one
# real way to get here without fabricating a baseline by hand.
# ------------------------------------------------------------

$ rm -f output/design_data.json output/*.docx
$ mkdir -p /tmp/design_hld_only_src
$ printf 'Returns Processing Service - High-Level Architecture Only\n\nThis write-up describes ONLY the high-level solution architecture for the Returns Processing Service. No implementation-level detail (API contracts, database schemas, sequence diagrams) is provided or intended here -- this is an HLD-only source document, not a combined design.\n\nThe service accepts a customer return request from the Storefront, validates it against the original order via the Order Service, issues a refund through the Payment Gateway, and restocks inventory via the Inventory Service once the returned item is received and inspected. It must be resilient to brief Payment Gateway outages (queue and retry rather than fail the return outright) and must comply with PCI-DSS for any payment-related data it touches.\n' > /tmp/design_hld_only_src/returns_service_hld.txt

# F1. POSITIVE: import, EXPLICITLY scoped to "High-Level Design only" -- Design_Import_Agent's own
# STEP 3B gives an explicit document_type in the request precedence over its own inference, so this
# should persist document_type="HLD" with no low_level_design content at all.
Import the design documented in /tmp/design_hld_only_src as a High-Level Design only -- there is \
no low-level design content in this source, and none should be invented.

# F2. NEGATIVE: explicitly ask to regenerate just the LLD against that HLD-only baseline -- must be
# a hard, explicit ERROR (a document titled "Low-Level Design" with nothing in it would be actively
# misleading), not a silently-empty document and not a silent fallback to rendering the HLD instead.
Please regenerate just the LLD.

# F3. POSITIVE: the SAME baseline, but asking for the HLD instead -- confirms an HLD-only baseline
# still renders successfully; the ERROR in F2 is specific to the LLD request, not the baseline itself.
Please regenerate just the HLD.

# Confirm manually: exactly one file, an HLD, should appear below -- no LLD file at all.
list

# ------------------------------------------------------------
# cleanup
# ------------------------------------------------------------
$ rm -f output/design_data.json output/requirements_summary.json output/cloudarch_drawio.xml
$ rm -f output/*.docx
$ rm -rf /tmp/design_hld_only_src
exit
