# ============================================================
# Business process management robustness test script
#
# Run from samples/Neurosan/ProcessEngineering:
#   uv run python cli.py -f examples/Tests/process_cli_test_commands.txt
#
# Exercises every process.hocon-family network end to end: Process_Pipeline (creation),
# Process_Consultant_Agent (read-only Q&A), Regenerate_Document_Agent (bare document
# re-render), Subprocess_Driver_Agent_Main (standalone level-2/3 subprocess expansion, via
# /process_subprocess_regenerate -- NOT the same thing as a full pipeline re-run),
# Process_Update_Pipeline (modification), Process_Simulation_Query_Agent,
# Process_Scenario_Tester (what-if), and Process_Import_Agent. Also exercises the
# process_architect.hocon router's own domain-disambiguation rules specific to the process
# domain: the UNCONDITIONAL "no process/design word -> always ask" gate on Process_Update_
# Pipeline (process_architect.hocon's own "2a/2b: WHY THE GATE ABOVE HAS NO STATE-BASED
# EXCEPTION" -- a real production bug that took THREE rounds of fixes, where a
# domain-word-free request was repeatedly routed to Process_Update_Pipeline on a guess
# about session state and silently fabricated an unrelated new process from scratch), and
# a what-if domain crossover between Process_Scenario_Tester and Design_Scenario_Tester
# (the same category of bug togaf_cli_test_commands.txt's own Part H already covers for
# TOGAF vs Design, exercised here from the Process vs Design angle instead -- not
# previously covered by any existing test script in this project).
#
# Test fixture: "Vendor Onboarding" -- reused verbatim from process.hocon's/process_update.
# hocon's/process_consultant.hocon's/process_simulation_query.hocon's/process_scenario_
# tester.hocon's own sample_queries (KYC checks, contract approval, a background-check
# step, a Compliance team, bottleneck simulation) so every part of this script exercises
# content each network's own instructions were actually written to expect, rather than an
# unrelated theme. The domain-crossover Part (D) and the import Part (J) each introduce
# their own small, clearly distinct fixture (a "Document Verification Service" design, and
# a short "Expense Approval" process respectively) so neither is confused with the primary
# Vendor Onboarding baseline.
#
# Session state in this CLI is a mix of in-memory conversation (reset by "clear") and
# on-disk saved JSON (output/process_data.json, output/design_data.json, independent of
# "clear"). The $ resets below delete the on-disk state at specific points so the
# nothing-saved negative cases, the import test, and the domain-crossover fixture are each
# exercised against a genuinely clean slate rather than leftover state from an earlier part
# of this same script.
# ============================================================

# B1. POSITIVE: a real, substantive request -- elaborates process.hocon's own canonical
# sample_query ("Create a process for onboarding new vendors, including KYC checks and
# contract approval.") with named roles, an approval gate, and an SLA so the generated
# process isn't thin, and so later parts (C, D, G, H, I) have real steps/roles to query,
# simulate, modify, and ask what-if questions against.
Create a process for onboarding new vendors. Procurement initiates the request and submits \
the vendor's registration details. The Compliance team then performs KYC (Know Your Customer) \
checks and a sanctions-list screening. Once KYC clears, Legal drafts and negotiates the supply \
contract with the vendor. A Finance Director must give final contract approval before the vendor \
is activated in the system. Finance then sets up the vendor's payment details and the vendor is \
notified it can begin fulfilling orders. The whole process, from initial registration to vendor \
activation, must complete within 5 business days for 95% of vendors, and any step blocked for \
more than 2 business days must be escalated to the Procurement Director.
