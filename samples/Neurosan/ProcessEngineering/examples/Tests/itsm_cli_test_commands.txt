# ============================================================
# ITSM process document generation robustness test script
#
# Run from samples/Neurosan/ProcessEngineering:
#   uv run python cli.py -f examples/Tests/itsm_cli_test_commands.txt
#
# Exercises ITSM_Pipeline, ITSM_Compliance_Agent/ITSM_Simulation_Agent (internal, never called
# directly), ITSM_Update_Pipeline, ITSM_Import_Agent, ITSM_Consultant_Agent, ITSM_Reviewer_Agent,
# ITSM_Scenario_Tester, and ITSM_Simulation_Query_Agent end to end: nothing-saved negative cases
# (generate/regenerate/update/consult/review/what-if/simulate, each against a genuinely clean
# slate), a real creation run authored fresh from an inline brief (ITSM has no "derive from an
# existing design/requirements document" source the way TOGAF does -- see ITSM_Analysis_Agent's own
# NO REAL SOURCE MATERIAL stop condition, exercised directly in Part A), the deliberate ITIL scope
# disclosure (Capacity/Availability/CSI/Financial-Management/Release-Deployment/Knowledge-Management
# all out of scope), a single-document regeneration (ITSM has no Vision/Definition- or HLD/LLD-style
# variant split -- always exactly one document), an explicit update request proving ITSM_Agent's
# UPDATE DELTA branch preserves unrelated content, an import negative case (no directory exists),
# consultant/reviewer/scenario-tester/simulation-query positive queries directly exercising this
# project's own sample_queries from itsm.hocon/itsm_consultant.hocon/itsm_reviewer.hocon/
# itsm_scenario_tester.hocon/itsm_simulation_query.hocon, and domain-crossover disambiguation
# between ITSM_Scenario_Tester and the generic process Scenario_Tester.
#
# Test fixture: a small inline ITSM brief, written by this script itself -- a mid-size SaaS
# company ("Northwind Checkout Platform") with a Service Desk role and a Checkout DB configuration
# item, deliberately chosen so the resulting ITSM content genuinely supports
# itsm_scenario_tester.hocon's own two sample_queries ("What happens if the Service Desk role is
# unavailable?" / "What is the impact of the Checkout DB configuration item failing?") and
# itsm_simulation_query.hocon's own sample_query, rather than those sample queries being untestable
# against a differently-themed fixture. Mirrors togaf_cli_test_commands.txt's own identical
# reasoning for its "Supplier Onboarding Service" fixture.
#
# Session state in this CLI is a mix of in-memory conversation (reset by "clear") and on-disk saved
# JSON (output/itsm_data.json, output/process_data.json, independent of "clear"). The $ resets
# below delete the on-disk state at specific points so the nothing-saved negative cases are
# exercised against a genuinely clean slate rather than leftover state from an earlier part of this
# same script.
#
# This script calls "clear" between every Part boundary from Part B onward -- same reasoning as
# togaf_cli_test_commands.txt's own header comment: ITSM_Pipeline's own generate/compliance/
# simulation loop is itself a multi-agent exchange whose conversation history grows large, and
# every later turn in the SAME session would otherwise resend that entire history as context even
# though every ITSM-domain network reads everything it needs straight from disk
# (load_master_itsm_json/load_full_itsm_context), never from chat history.
# ============================================================

$ rm -f output/itsm_data.json output/process_data.json output/requirements_summary.json
$ rm -f output/*.docx
sleep 1

# ------------------------------------------------------------
# PART A -- negative / edge cases (nothing saved yet)
# ------------------------------------------------------------

# A1. NEGATIVE: a bare creation instruction with no real content behind it at all -- must trigger
# ITSM_Analysis_Agent's own NO REAL SOURCE MATERIAL stop condition, not invent a plausible-sounding
# organization/service catalog from nothing.
Create an ITSM process document.

# A2. NEGATIVE: regenerate the ITSM document before anything has ever been created.
Regenerate the ITSM process document.

# A3. NEGATIVE: explicit update request against nothing saved -- must explain that no saved ITSM
# process document exists and must NOT create one as a substitute.
Add an emergency change type to the ITSM process document.

# A4. NEGATIVE: consultant query with nothing saved -- ITSM_Consultant_Agent's own "I cannot see
# any ITSM process document data" message, not a guess.
Who is accountable for approving emergency changes in the ITSM process document?

# A5. NEGATIVE: quality-review request with nothing saved.
Review the ITSM process document for quality.

# A6. NEGATIVE: what-if scenario query with nothing saved -- ITSM_Scenario_Tester's own "I cannot
# see any ITSM process document data" message.
What happens if the Service Desk role is unavailable?

# A7. NEGATIVE: structural risk/coverage analysis query with nothing saved.
Analyze the ITSM process document for bottlenecks and coverage gaps.

# A8. NEGATIVE: import from a directory that does not exist -- must report NOT_FOUND plainly, not
# fabricate content.
Import the ITSM process documented in ./this-directory-does-not-exist as an ITSM process document.

# A9. NEGATIVE: genuinely ambiguous intent -- should ask what the user wants, not guess.
Can you take a look at this and tell me what you think?

# A10. GENERAL (dual-mode consultant): a purely general ITSM/ITIL question, with NOTHING saved
# yet, must be answered directly from best-practice knowledge -- ITSM_Consultant_Agent must NOT
# refuse this for lack of a saved document, since the question doesn't need one.
What are the core phases of incident management, and how should escalation tiers typically work?

clear

# ------------------------------------------------------------
# PART B -- ITSM creation (positive), authored fresh from an inline brief
# ------------------------------------------------------------

# B1. POSITIVE: a real, substantive ITSM brief with enough content to populate the service catalog,
# incident/problem/change/request-fulfillment process steps, SLAs, a light CMDB, and RACI --
# deliberately itemized (rather than one dense paragraph), same reasoning as
# togaf_cli_test_commands.txt's own Part B1 comment: explicit itemization avoids the kind of
# conservative "requirements could not be extracted" bail-out a thinner request risks triggering.
Create an ITSM process document for Northwind Checkout Platform, a mid-size SaaS company. \
Services: Checkout API (business-critical, owned by the Payments team) and Customer Portal \
(business-critical, owned by the Web team). Roles: a Service Desk (first-line incident intake and \
triage, escalation tier 1), a Payments Engineering On-Call (tier 2 for Checkout API incidents), and \
a Change Advisory Board chaired by the Head of Engineering. Incident management should cover a \
standard P1-P4 priority scheme with response/resolution targets, and escalate from the Service Desk \
to Payments Engineering On-Call when a P1/P2 isn't acknowledged within target. Problem management \
should track known errors linked back to recurring incidents. Change management should have \
standard, normal, and emergency change types, each with a defined CAB approval path, and a risk \
assessment scheme for normal/emergency changes. Request fulfillment should cover access requests \
and configuration changes with target fulfillment times. Define SLAs for both services' own \
uptime and P1 response time, with a defined measurement window for each. The CMDB should include a \
Checkout DB configuration item that the Checkout API depends on, and a Payment Gateway Integration \
configuration item that the Checkout API also depends on. Include a RACI matrix covering each \
process area, a tooling inventory (ticketing, monitoring, CI/CD), and the known risks and controls \
for this setup.

# Confirm manually: the listing below should show ONE ITSM process document file (ITSM has no
# Vision/Definition- or HLD/LLD-style variant split), safe-filenamed from the organization's own
# real name -- never a filename containing "ITSM" or "ITSM Process Document" itself (document-
# metadata naming hygiene).
list

# B2. Scope disclosure check: a request that explicitly names the out-of-scope ITIL practices
# should get a plain statement that this generator's scope is deliberately limited, not a
# confident claim that it already covers them.
Does the ITSM process document include Capacity Management, Availability Management, Continual \
Service Improvement, Financial Management for IT Services, Release/Deployment management, or \
Knowledge Management?

clear
sleep 10

# ------------------------------------------------------------
# PART C -- ITSM_Scenario_Tester what-if queries (grounded in Part B's own real RACI/escalation/CI
# links, directly exercising itsm_scenario_tester.hocon's own sample_queries)
# ------------------------------------------------------------

What happens if the Service Desk role is unavailable?

sleep 5

What is the impact of the Checkout DB configuration item failing?

sleep 5

# C3. Must decline a quantitative estimate -- qualitative dependency tracing only, per
# itsm_scenario_tester.hocon's own instructions.
How likely is it that the Checkout DB configuration item failing would cause a full outage?

clear

# ------------------------------------------------------------
# PART D -- ITSM_Simulation_Query_Agent (structural risk/coverage analysis over the Part B baseline)
# ------------------------------------------------------------

Analyze the ITSM process document for bottlenecks and coverage gaps.

clear

# ------------------------------------------------------------
# PART E -- ITSM_Consultant_Agent (general explanation of the Part B baseline)
# ------------------------------------------------------------

Who is accountable for approving emergency changes?

sleep 5

What is the SLA target and measurement window for Checkout API's own P1 response?

clear

# ------------------------------------------------------------
# PART F -- ITSM_Reviewer_Agent (quality audit, read-only mode then explicit apply mode)
# ------------------------------------------------------------

# F1. READ-ONLY (default): a plain quality-review request must return findings only, with no
# persisted change.
Review the ITSM process document for quality.

sleep 5

# F2. APPLY MODE: only when explicitly asked to fix, the reviewer applies mechanical, well-grounded
# corrections and reports what changed -- see reviewer_agent.txt's own APPLY MODE rules.
Review the ITSM process document for quality and fix any mechanical issues you find.

clear

# ------------------------------------------------------------
# PART G -- explicit update request (ITSM_Agent's UPDATE DELTA branch): confirms an update
# preserves unrelated content rather than rebuilding from scratch.
# ------------------------------------------------------------

# G1. POSITIVE: a real, specific change request against the Part B baseline, grounded in a real
# CAB reference from that baseline -- not a generic "add a change type" request.
$ rm -f output/*.docx
Add an emergency change type to the ITSM process document, requiring sign-off from the Change \
Advisory Board chair in addition to the standard emergency approval path. Keep everything else \
unchanged.

# G2. Confirm the change is actually persisted and the document still renders correctly.
Regenerate the ITSM process document.

list

clear

# ------------------------------------------------------------
# PART H -- domain disambiguation (ITSM signal words vs. the generic PROCESS domain, and ITSM
# what-if crossover must not bleed either direction)
# ------------------------------------------------------------

# H1. Build a plain business process so Scenario_Tester has something real to answer against,
# alongside the Part B/G ITSM process document that is also currently saved.
Create a workflow for onboarding a new engineer, covering account provisioning, equipment \
issuance, and a 30-day check-in with their manager.

# H2. DOMAIN CROSSOVER: a question naming an ITSM-specific role/CI must route to
# ITSM_Scenario_Tester, NOT Scenario_Tester, even though a plain business process is also saved
# right now.
What happens if the Service Desk role is unavailable?

# H3. DOMAIN CROSSOVER (the reverse direction): a question about the ONBOARDING workflow, with no
# ITSM-specific wording at all, must route to Scenario_Tester, NOT ITSM_Scenario_Tester.
What happens if the 30-day check-in step is skipped?

# H4. Confirms "ITSM" itself, not bare "process", is the deciding signal word -- this request names
# "process" but is unambiguously the ITSM domain.
Create an ITSM process document covering incident and change management for a different company.

# ------------------------------------------------------------
# cleanup
# ------------------------------------------------------------
$ rm -f output/itsm_data.json output/process_data.json output/requirements_summary.json
$ rm -f output/*.docx
exit
