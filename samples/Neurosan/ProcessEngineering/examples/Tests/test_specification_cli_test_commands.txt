# ============================================================
# Test Specification robustness test script
#
# Run from samples/Neurosan/ProcessEngineering:
#   uv run python cli.py -f examples/Tests/test_specification_cli_test_commands.txt
#
# Exercises Test_Specification_Agent, Test_Consultant_Agent, and
# Test_Reviewer_Agent end to end: missing-source edge cases, generation
# against one/two/three saved source artifacts, consultant queries,
# quality review (read-only and apply-mode fix), a separate later-turn
# standalone fix request, document regeneration, domain-crossover
# disambiguation (a saved test specification must not bleed into an
# unrelated requirements-domain question, and vice versa), and a
# bare-ambiguous-intent clarification check.
#
# Unlike rm_rtp_cli_test_commands.txt, this script does NOT depend on any
# pre-existing fixture files -- Test_Specification_Agent's own three
# source artifacts (a saved requirements summary, design document, and
# cloud architecture diagram) are built FRESH, in order, from one
# consistent fictional brief (a corporate travel-booking and
# expense-reconciliation platform), so the generated test cases trace to
# real, topically-coherent requirement ids and component names rather
# than two unrelated fixtures stitched together. This means Part B below
# runs the REAL requirements/design/cloud-architecture creation
# pipelines, each a genuine multi-agent generate/review loop -- expect
# this script to take considerably longer end to end than
# rm_rtp_cli_test_commands.txt's own already-long run.
#
# Session state in this CLI is a mix of in-memory conversation (reset by
# "clear") and on-disk saved JSON (output/requirements_summary.json,
# output/design_data.json, output/cloudarch_drawio.xml,
# output/test_specification.json, independent of "clear"). The $ resets
# below delete the on-disk state at specific points so the "nothing
# saved yet" negative cases, and the partial-source case in Part G, are
# exercised against a genuinely clean slate rather than leftover state
# from an earlier run of this same script.
# ============================================================

$ rm -f output/requirements_summary.json output/design_data.json output/cloudarch_drawio.xml output/test_specification.json
$ rm -f output/*.docx
sleep 1

# ------------------------------------------------------------
# PART A -- negative / edge cases (nothing saved yet)
# ------------------------------------------------------------

# A1. NEGATIVE: ask to generate a test specification with absolutely nothing saved
Create a test specification for the saved requirements.

# A2. NEGATIVE: consultant query with nothing saved yet
What's in the saved test specification?

# A3. NEGATIVE: reviewer query with nothing saved yet
Review the test specification for quality.

# A4. NEGATIVE: regenerate the test specification document before anything has ever been created
Regenerate the test specification document.

# A5. NEGATIVE: genuinely ambiguous intent -- should ask what the user wants, not guess
Can you take a look at this and tell me what you think?

# ------------------------------------------------------------
# PART B -- build the three source artifacts, from one consistent brief
# ------------------------------------------------------------

# B1. Synthesize and save a requirements register from a plain-language description (no files
# needed -- Requirements_Doc_Pipeline saves to the same requirements_summary.json state
# Test_Specification_Agent itself reads), and render the requirements document in the same call.
Create a requirements document for a new corporate travel-booking and expense-reconciliation \
platform called TravelLedger, for a mid-sized professional-services firm. It needs to let \
employees book flights/hotels/rail through a managed travel desk, submit expense claims with \
receipt capture, and route approvals to the right manager and finance cost center. It must comply \
with PCI-DSS for any stored payment card data, GDPR for EU traveler personal data, and SOX-aligned \
internal controls for expense approval segregation of duties. Flag any conflicts between a fast \
approval SLA and a strict multi-level approval control.

# B2. Create a design document FOR THE SAME SYSTEM, reusing the saved requirements summary --
# exercises the real design-creation pipeline against real requirement ids (FR-*/NFR-*/CON-*)
# from B1, not a generic brief.
Create a High-Level and Low-Level Design document for TravelLedger on AWS, using the saved \
requirements summary for scope and compliance requirements.

# B3. Generate a cloud architecture diagram from the design document just created.
Generate a cloud architecture diagram for the current design document.

list

# ------------------------------------------------------------
# PART C -- test specification generation (positive, all three sources present)
# ------------------------------------------------------------

# C1. POSITIVE: all three source artifacts exist -- confirms source_requirements_used,
# source_design_used, and source_cloudarch_used all come back true, and test cases trace to
# real ids/component names from Part B rather than anything invented.
Create a test specification for the saved requirements, design, and cloud architecture.

# ------------------------------------------------------------
# PART D -- test consultant queries against the saved specification
# ------------------------------------------------------------

What's in the saved test specification?
What test cases cover the PCI-DSS requirement?
What's not yet covered by a test case?
What testing risks or open questions were flagged?

# ------------------------------------------------------------
# PART E -- quality review (read-only, then apply-mode fix, then a separate standalone fix)
# ------------------------------------------------------------

# E1. Quality review, READ-ONLY (no fix requested -- must not touch the saved specification)
Review the test specification for quality.

# E2. Quality review AND fix in the SAME request
Review the test specification for quality and fix any issues you find, including any test cases \
with a vague or unverifiable expected result, or a coverage claim that doesn't match the actual \
test cases.

# E3. SEPARATE follow-up turn: a specific fix request, not combined with "review" this time
Update the test specification so the test case covering the approval-SLA-vs-segregation-of-duties \
conflict is marked as critical priority, and tell me exactly what you changed.

# ------------------------------------------------------------
# PART F -- document regeneration
# ------------------------------------------------------------

# F1. POSITIVE: document generation -- confirms the applied fixes show up, and the title/filename
# reflect the specification's own "name" field rather than a generic default.
Regenerate the test specification document.

list

# ------------------------------------------------------------
# PART G -- partial-source case (only requirements saved; no design, no cloud architecture)
# ------------------------------------------------------------

# G1. Drop the design and cloud-architecture artifacts, keep only the requirements summary, and
# force a fresh generation -- confirms Test_Specification_Agent handles ANY subset of its three
# sources gracefully (source_design_used/source_cloudarch_used both false, and their own
# coverage_summary lists both empty) rather than requiring all three or erroring.
$ rm -f output/design_data.json output/cloudarch_drawio.xml output/test_specification.json
Create a test specification for the saved requirements only.

What's in the saved test specification?

# ------------------------------------------------------------
# PART H -- domain disambiguation (crossover must not bleed either direction)
# ------------------------------------------------------------

# H1. DOMAIN CROSSOVER: a question naming "the saved requirements summary" must route to
# Requirements_Consultant_Agent, NOT Test_Consultant_Agent, even though a test specification is
# also saved right now and the wording ("requirements") appears in both domains' own vocabulary.
What's in the saved requirements summary?

# H2. DOMAIN CROSSOVER (the reverse direction): a question naming "the saved test specification"
# must route to Test_Consultant_Agent, NOT Requirements_Consultant_Agent, even immediately after
# H1's own requirements-domain answer.
What's in the saved test specification?

# ------------------------------------------------------------
# cleanup
# ------------------------------------------------------------
exit
