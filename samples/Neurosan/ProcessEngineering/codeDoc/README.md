# ProcessEngineering (neuro-san) -- structure diagrams

These diagrams document the Python declarations under `coded_tools/`, `cli.py`, and `tests/`, and
this project's declarative HOCON network composition under `registries/`:

- [Class inventory](class-inventory.md) lists every class declaration with its source location and
  declared base.
- [Class hierarchy](class-hierarchy.md) shows all declarations and actual inheritance/composition.
- [Application class diagram](application-classes.md) focuses on the application classes, with
  useful members and source-supported composition.
- [Network composition](network-composition.md) shows the sixteen agent networks' own front-man
  sequencing -- the neuro-san equivalent of an ADK-style `SequentialAgent`/`LoopAgent` composition
  diagram, re-expressed for a framework with no such runtime composition object (every sequence
  below is a convention a front-man's own instructions follow, not a Python object tree).

The hierarchy distinguishes project classes from external bases by labeling the external package in
each node. Composition edges are included only where construction or typed fields establish the
relationship; agent/tool names alone are not treated as class relationships.

This project's own class inventory (34 classes, scoped to exclude the neuro-san-studio scaffolding
this project didn't write) is considerably flatter than the ADK version's (61 classes across a
real `LlmAgent`/`BaseAgent`/pydantic-schema hierarchy): neuro-san's `CodedTool` interface is a
single-method entry point (`invoke(args, sly_data)`), so 30 of the 34 are direct, sibling
subclasses of the same external base with essentially identical shape. The Mermaid diagrams render
on GitHub; no local Mermaid/PlantUML renderer was available when these were prepared.

## Physical PNG diagrams

Rendered, standalone images generated by [`generate_diagrams.py`](generate_diagrams.py) (pure
matplotlib -- same approach `coded_tools/common/docgen/uml_diagrams.py` already uses for runtime
design-document diagrams, no Graphviz/PlantUML binary required). Re-run it after a structural
change:
```
cd samples/Neurosan/ProcessEngineering && uv run python codeDoc/generate_diagrams.py
```

- [`class-diagram.png`](class-diagram.png) -- the same 34 application classes as
  [application-classes.md](application-classes.md), rendered as a physical UML class diagram
  (inheritance/composition arrows; the 30 near-identical `CodedTool` leaves collapsed into 5
  cluster boxes by network area so the diagram doesn't repeat the same shape 30 times).
- [`sequence-cloudarch-pipeline.png`](sequence-cloudarch-pipeline.png) -- full detail for
  `CloudArch_Pipeline` (generator/reviewer/`loop_control`), including the review loop's frame.
- [`sequence-process-create.png`](sequence-process-create.png) /
  [`sequence-process-update.png`](sequence-process-update.png) /
  [`sequence-design-doc-create.png`](sequence-design-doc-create.png) /
  [`sequence-design-doc-update.png`](sequence-design-doc-update.png) -- stage-level sequence
  diagrams for the other four pipelines. Each generate/review cycle is shown as a dashed loop frame
  around the repeating messages, labeled with its stop condition and iteration cap -- see
  [network-composition.md](network-composition.md) for why that shape repeats across all five
  pipelines.

Arrows in the sequence diagrams show the order a front-man's own HOCON `"instructions"` call its
tools in, not literal Python method calls between siblings -- the actual caller in every case is
the LLM itself, re-evaluating those instructions on every turn. There is no runtime orchestrator
object the way ADK's `SequentialAgent`/`LoopAgent` was; `loop_control`'s own hard iteration-count
check is the only enforcement mechanism beyond the model actually following its instructions (see
the main README's "Why neuro-san needed a different design for the generate/review loop").
