# ProcessEngineering Python UML

Structure diagrams for this sample's own code: the ADK agent/class hierarchy, how those classes
compose into runtime pipelines, and physical UML renderings of both.

- [Class inventory](class-inventory.md) — every class declaration, its source file, and its declared base.
- [Class hierarchy](class-hierarchy.md) — all declarations and their actual inheritance, including test fixtures.
- [Application class diagram](application-classes.md) — the application classes only, with their useful members and source-supported composition relationships.
- [ADK composition](adk-composition.md) — the major runtime agent pipelines and how they compose via `SequentialAgent`/`LoopAgent`.

The hierarchy labels each node with its external package where a class comes from outside this project — `Agent` is shown as the ADK-declared base for `DefaultAgent`; the source documents `google.adk.agents.Agent` as an alias of `LlmAgent`. Composition edges are included only where construction or a typed field actually establishes the relationship; sharing an agent name alone is not treated as a class relationship.

The inventory covers 61 `class` statements across the application and test Python files. There are no `@dataclass` declarations or enum subclasses. Functions, module-level agent registries, and other non-class structures are out of scope. The Mermaid diagrams render directly on GitHub.

## Physical PNG diagrams

Rendered, standalone images generated by [`generate_diagrams.py`](generate_diagrams.py) (pure matplotlib — the same approach `process_agents/common/uml_diagram_agent.py` uses for runtime design-document diagrams, so no Graphviz/PlantUML binary is required). Re-run it after any structural change:

```
cd samples/GCP/ProcessEngineering && .venv/bin/python codeDoc/generate_diagrams.py
```

- [`class-diagram.png`](class-diagram.png) — the same 13 application classes as [application-classes.md](application-classes.md), rendered as a physical UML class diagram (inheritance/composition/dependency arrows).
- [`sequence-cloudarch-pipeline.png`](sequence-cloudarch-pipeline.png) — full agent-level detail for `CloudArch_Pipeline` (generator / reviewer / stop controller), including the review `LoopAgent`'s loop frame.
- [`sequence-process-create.png`](sequence-process-create.png) / [`sequence-process-update.png`](sequence-process-update.png) / [`sequence-design-doc-create.png`](sequence-design-doc-create.png) / [`sequence-design-doc-update.png`](sequence-design-doc-update.png) — stage-level sequence diagrams for the other four pipelines. Each `LoopAgent` stage (review loop, JSON normalization loop) is shown as one collapsed lifeline whose label lists its internal agent order and iteration cap, rather than as separate lifelines per inner agent — see [adk-composition.md](adk-composition.md) for why those stages repeat nearly the same shape across all four pipelines.

Arrows in the sequence diagrams show execution order through the parent `SequentialAgent`/`LoopAgent`'s `sub_agents` list, not literal Python method calls between siblings. The actual caller in every case is the ADK orchestrator object, which is omitted as its own lifeline since it never does anything but dispatch to the next child in order.
